# Blinding controls needed before Book 1A Phase 1 (Kyron, Nov 4, 2026)

Status: **documented, not yet set up.** Book 1A Phase 1 should not start until items 1-6 are in place and checked.

## Why
Phase 0 ran inside `K:\Databento_BackTesting\Book1A\code`, a worktree whose folder sits inside the Book 1 project.
Three leaks came from that, all logged in `P0.1_blind_run_setup.md` (events 5, 6, 7):
- every session start shows the Book 1 repository's git status and recent commit subjects, and those subjects state
  Book 1 results (the Phase 4 holdout verdict, the failing test, the losing day and its size);
- the Book 1 `CLAUDE.md` and the Book 1 auto-memory load with the parent folder, and they point to the Book 1 result
  files;
- `BOOK1_ROOT = K:\Databento_BackTesting` gives the runner read access to the whole Book 1 tree, results included.
No Book 1 result file was opened, but the commit subjects were seen. Rewriting Book 1's history is not allowed, so the
fix is to keep the Book 1A runner away from it.

## Controls

| # | Control | How | Check before Phase 1 |
|---|---|---|---|
| 1 | Fresh, isolated working folder outside the Book 1 tree | A new clone of `kevo84-prog/NT82` branch `book1a-phase0-pc` (or the Phase 0 freeze tag once applied) into a folder that is not under `K:\Databento_BackTesting`, e.g. `K:\Book1A_runner\code`. Its own `.venv`. The Claude session opens that folder only. | `git -C <runner> log` shows only Book 1A history; the session-start git status is the runner repo's. |
| 2 | No result-bearing commit messages in view | The runner never runs `git` in the Book 1 repository (no `log`, `show`, `diff`, `blame`, `status`). The runner folder is not a worktree of the Book 1 repo. | Session start shows no Book 1 commit subject. |
| 3 | Book 1 inputs only, through a narrow read-only root | A folder `K:\Book1A_inputs\` holding read-only links (junctions) to exactly: `raw\block1\`, `tapes\` (E5: kept as Book 1 built them), `jeron_engine\`, `jeron_harness\build\` and `jeron_harness\nt_source\`, `gex_levels_block1.csv`, `econ_calendar_2025-10_2026-04.csv`, the gate 6 integrity table. `BOOK1_ROOT` points there. Nothing else from Book 1. | A listing of `K:\Book1A_inputs\` matches this list; manifests (P0.2) still match. |
| 4 | Result files out of reach | Not linked, not copied: `BOOK1_RESULTS_PRIVATE.md`, `FROZEN_STRATEGY.md`, `backtest\phase1..4\` run and result folders, `backtest\research\`, the Drive `Phase N - <name>` result folders, Book 1 day sheets, reports, trade lists, `JOFS_*` logs of Book 1 runs, the Book 1 `.git`. | A scripted check that none of these paths resolves from the runner folder or `BOOK1_ROOT` (to be written with the setup). |
| 5 | Rules and memory | The runner folder's `CLAUDE.md` = the Book 1A rules only (no pointer to Book 1 result files). A new folder gets its own Claude auto-memory, so the Book 1 memory index does not load. | Session context shows only the Book 1A `CLAUDE.md`. |
| 6 | Checker stays separate | `K:\Book1A_checker\` keeps the Book 1 reference ledgers and does every P0.4-type comparison. The runner only writes `checker_input\` and copies `checker_output\` files unopened. | No checker reference file is linked into the runner folder. |
| 7 | Book 1A's own commit messages | No P&L, R, win rate or pass / fail of a result in a commit subject, while the next phase is still blind. Results go in the phase's result file, written after the run. | Review the subjects before each push. |
| 8 | Access log continues | Every exposure (seen by accident, shown by a tool) goes into the P0.1 access log, with what was seen and that it was not used. | Log entry for the first Phase 1 session. |
